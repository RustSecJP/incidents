# RUSTSEC-2026-0349: `rustls` で、認証前の ServerHello によって、以後の接続が従来の鍵交換に格下げされる

## 要約

rustls のクライアントは、相手のサーバーを認証する前に、そのサーバーが選んだ鍵交換の方式を覚えていました。ネットワーク上の攻撃者は、これを使って、そのサーバー名への以後の接続を、耐量子（X25519MLKEM768）ではない従来の X25519 だけの鍵交換にさせることができます。

鍵が漏れるわけでも、認証を回避されるわけでもありません。失われるのは「今の通信を保存しておき、将来量子計算機で解読する」攻撃への備えだけです。

## 自分が影響を受けたかの確かめ方

```shell
cargo tree -i rustls --depth 0
```

0.23.46 より前の版をクライアントとして使い、セッションの再開（resumption）を有効にしている場合は、影響を受けます。サーバーとしてだけ使っている場合は当たりません。

## 直し方

```shell
cargo update -p rustls
```

0.23.46 以上になったことを確かめます。すぐに上げられない場合は、クライアントでセッションの再開を無効にすると、記録が残らないので影響を受けません。

## 原文の訳

クライアントは ServerHello を処理するとき、サーバーを認証する前に、サーバー名ごとに、サーバーが選んだ鍵交換のグループを記録していました。この記録は、そのサーバー名に対する以後の ClientHello で、どの鍵共有（key share）を送るかを予測するのに使われます。

ネットワーク上の攻撃者は、ある接続の試みに対して X25519 を選ぶ ServerHello を返し、そのまま接続を切ることができます。すると、そのサーバー名に対する以後の ClientHello には X25519 の鍵共有だけが入ります。一方で `supported_groups` には、まだ X25519MLKEM768 が先頭に書かれています。本物のサーバーが、自分が望む混合（hybrid）グループを求める HelloRetryRequest を送らずにその鍵共有を受け入れると、ハンドシェイクは従来の方式だけの鍵交換で、エラーもなく終わります。この状態は、その記録がクライアントのセッションの保存先に残っている間、続きます。

影響は、影響を受けた接続で耐量子の機密性が失われることです（「今集めて、あとで解読する」攻撃）。鍵が漏れることも、認証を回避されることもありません。

次のものは影響を受けません。

- 自分が望むグループを求める HelloRetryRequest を送るサーバーへの接続
- セッションの再開を無効にしたクライアント（何も記録しないため）
- ほかのサーバー名

この動きは [draft-ietf-tls-key-share-prediction](https://www.ietf.org/archive/id/draft-ietf-tls-key-share-prediction-01.html#name-security-considerations) で論じられており、実際の影響はサーバーの方針に大きく左右されます。
