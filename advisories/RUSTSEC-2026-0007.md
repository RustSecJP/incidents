# RUSTSEC-2026-0007: `bytes` の `BytesMut::reserve` で整数があふれる

| | |
|---|---|
| crate | [`bytes`](https://crates.io/crates/bytes) |
| 種類 | メモリ破壊（整数のあふれ） |
| 助言の日付 | 2026-02-03 |
| 影響を受ける版 | 1.2.1 以上、1.11.1 より前 |
| 直った版 | `1.11.1` 以上 |
| 別の番号 | CVE-2026-25541、GHSA-434x-w66g-qw3r |
| 原文 | [RUSTSEC-2026-0007](https://rustsec.org/advisories/RUSTSEC-2026-0007.html)（CC BY 4.0。GitHub Security Advisory をもとにした内容） |

## 要約

`BytesMut::reserve` に非常に大きな値を渡すと、内部の足し算があふれます。その結果、確保した領域より大きな容量を持っていると思い込み、その後の操作で領域の外を読み書きすることがあります（未定義動作）。

起きるのは、整数のあふれが「折り返す」設定のときだけです。リリースビルドの既定はこちらです。デバッグビルドでは、あふれた時点でパニックになるので起きません。

## 自分が影響を受けたかの確かめ方

```shell
cargo tree -i bytes --depth 0
```

1.2.1 以上、1.11.1 より前の版なら影響を受けます。`reserve` に外から来た大きさをそのまま渡しているコードがあるかも確かめます。

## 直し方

```shell
cargo update -p bytes
```

1.11.1 以上になったことを確かめます。

すぐに上げられない場合は、`Cargo.toml` の `[profile.release]` に `overflow-checks = true` を足すと、あふれた時点でパニックになり、この問題は起きなくなります（その分、少し遅くなります）。

## 原文の訳

`BytesMut::reserve` の、所有者が自分だけのときに領域を取り戻す処理では、次の条件が、あふれを確かめない足し算を使っています。

```rs
if v_capacity >= new_cap + offset
```

リリースビルドで `new_cap + offset` が `usize` からあふれると、この条件が誤って成り立つことがあります。すると `self.cap` が、実際に確保した容量より大きな値になります。その後、`spare_capacity_mut()` などの API がこの壊れた `cap` を信じて、範囲外のスライスを作ることがあり、未定義動作になります。

この動きはリリースビルド（整数のあふれが折り返す）で起きます。デバッグビルドでは、あふれの確認があるのでパニックになります。

### 再現のコード

```rs
use bytes::*;

fn main() {
    let mut a = BytesMut::from(&b"hello world"[..]);
    let mut b = a.split_off(5);

    // b を、裏の領域の唯一の所有者にする
    drop(a);

    // reserve の中の new_cap + offset であふれを起こす
    b.reserve(usize::MAX - 6);

    // 壊れた cap を信じるので、未定義動作やヒープのあふれが起きうる
    b.put_u8(b'h');
}
```

### 回避策

`BytesMut::reserve` の利用者が影響を受けるのは、整数のあふれが折り返す設定のときだけです。あふれたときにパニックする設定なら、この問題は当てはまりません。
